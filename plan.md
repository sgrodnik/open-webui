# План работ

## Краткое описание проекта

Open WebUI — веб-интерфейс для работы с AI-моделями на SvelteKit, Svelte и TypeScript. Маршруты находятся в `src/routes`, UI-компоненты — в `src/lib/components`, клиентские API-обёртки — в `src/lib/apis`, общее состояние — в `src/lib/stores`, типы — в `src/lib/types`, локализация — в `src/lib/i18n`. Серверная часть проекта находится в `backend/`.

## Правила ведения плана

- Общаться и вести записи в этом файле на русском языке.
- Не начинать реализацию, пока пользователь явно не разрешил её.
- В разделе «Концепция» кратко описывать текущее состояние модифицированных частей: без истории изменений и без упоминания того, что не было добавлено.
- Одну идею вести итеративно: пользователь может уточнять требования после первой реализации, а последующие правки считаются продолжением той же задачи.
- Для одной идеи вести одну запись в журнале и не создавая отдельную запись на каждую итерацию.
- В журнале указывать только дату и шаг; подробности текущей функциональности описывать в концепции и не дублировать.
- Новые записи журнала размещать сверху.
- Сохранять краткость и ясность формулировок.

## Концепция

На мобильных устройствах свайп вправо или кнопка открытия панели показывают оригинальную боковую панель и полноэкранное окно с десятью последними чатами. На десктопе окно открывается кнопкой «Недавние чаты» в боковой панели и отображается поверх интерфейса в компактном формате. В первой строке карточки показаны название и первый запрос, а справа — время создания, количество запросов пользователя и время обновления. Если название является подстрокой первого запроса, отображается только первое слово названия, затем первый запрос без первого слова. Последний запрос занимает всю ширину второй строки; длинный текст визуально обрезается по ширине без лимита символов. В заголовке окна расположены числовые поля размера шрифтов, горизонтальных и вертикальных отступов, ширины и смещения окна со сбросом; настройки сохраняются между сессиями. Текущий чат обозначен 0, предыдущие — 1–9 по порядку переходов внутри текущей сессии; при старте страницы остальная очередность берётся с сервера. Цифры в окне выбирают чат; сочетания клавиши префикса с `1`–`9` переключают чат без показа окна. Тильда, клавиши «Ё» и грависа поддерживаются как префикс: двойное нажатие открывает окно. Первая клавиша префикса ожидает продолжения 500 мс, подсвечивая кнопку открытия; одиночный символ вводится в поле ввода. Escape закрывает окно.

## История изменений заметок

### Запрос
В общем окне заметок добавить кнопку «История», открывающую двухпанельный просмотр: слева хронологический список изменений по всем заметкам, справа — diff выбранного изменения. История нужна для просмотра действий модели и пользователя; восстановление заметок пока не входит в задачу.

### Предлагаемый подход
- Хранить изменения в журнале на бэкенде, рядом с основной базой заметок; отдельная полная копия заметки на каждую версию не нужна.
- В журнал записывать метаданные изменения (заметка, заголовок, время, по возможности источник изменения) и diff. Изменения создания и удаления тоже отображать; при физическом удалении заметки сначала сохранять diff удаления, чтобы запись истории пережила удаление.
- Создавать diff в общей точке обновления заметки на бэкенде, чтобы охватить изменения и из редактора, и из инструмента модели. Объединять частые автосохранения, чтобы журнал не засорялся.
- Для текста использовать посимвольную детализацию по видимым символам Unicode, сохраняя контекст строк или абзацев для читаемости.
- Git не обязателен: он потребовал бы экспорта записей БД в файлы и сам по себе не гарантирует хранение только diff. В добавленном diff неизбежно остаются новые или удалённые фрагменты текста.

## Семантический поиск по чатам

### Цель
Дополнить текущий лексический поиск семантическим, чтобы находить нужные разговоры по смыслу, даже если слова запроса не совпадают с формулировками в чате. Особенно важно находить отдельную задачу внутри многотемного сообщения и учитывать контекст коротких реплик вроде «расскажи подробнее».

### Целевая схема индексации
- Обрабатывать новые и изменённые чаты в фоне, а не запускать LLM и генерацию embeddings при каждом поисковом запросе. При обновлении переиндексировать только затронутый чат или его изменившиеся части.
- Перед векторизацией текстовая LLM анализирует диалог итеративно, в контексте всей беседы или скользящих окон. Короткие реплики и эллиптические формулировки связываются с предыдущим контекстом и преобразуются в самостоятельные поисковые формулировки.
- Многотемные сообщения разбиваются на атомарные смысловые фрагменты/утверждения. Сначала использовать явную структуру текста — заголовки, абзацы и пункты списков; длинные однородные фрагменты ограничивать по размеру с перекрытием. Не полагаться только на разбиение по фиксированному числу символов.
- Индексировать отдельные фрагменты, а не только один embedding всего чата. Для каждого фрагмента хранить связь с исходным сообщением, чатом и его позицией; embeddings фрагментов нужны для поиска конкретных тем и деталей.
- Сохранять исходные сообщения без изменений. Контекстное обогащение и выделенные LLM смысловые фрагменты используются только для поиска; найденный результат показывает исходный текст и при необходимости соседний контекст. Полный родительский текст остаётся в основной базе, поэтому в векторном индексе достаточно ссылки на него, а не ещё одной полной копии.
- LLM не должна добавлять факты, которых нет в исходном диалоге. Производные формулировки нужно валидировать и хранить с привязкой к источнику; ошибки обогащения не должны менять или подменять оригинал.

### Поиск и выдача результатов
- Использовать гибридное ранжирование: векторный поиск для смыслового сходства и текущий лексический поиск для точных фраз, имён, кодов и редких терминов. Векторное совпадение не считать гарантией точного совпадения по словам.
- Найденные микро-фрагменты группировать по чатам. В выдаче показывать чат и исходный фрагмент/контекст, соответствующий найденному дочернему фрагменту.
- Сохранять существующие фильтры поиска и проверять доступ пользователя как при поиске по векторам, так и при получении исходного чата. При изменении или удалении чата надёжно обновлять или удалять связанные индексные записи через фоновую обработку.
- Выбирать мультиязычную embedding-модель, пригодную для русского текста. При смене модели предусмотреть перестроение индекса.

### Ограничения и статус
Обогащение и разбиение моделью повышают качество поиска, но добавляют вычислительную стоимость, задержку индексации и возможность ошибок сегментации. Индексация должна быть асинхронной и повторяемой. Концепция согласована; реализация ещё не начата.
